# Polish Patterns

返信 draft の polish 技法集。 各 pattern は **before / after** で示す。

## 1. 削る patterns

### 1-1. 必要十分まで削る (= 受信者視点で何が要るか)

```
[before]
Caddy: web server / リバースプロキシ。 設定がシンプルで、 Let's Encrypt の
自動取得 + 更新が built-in なので、 数行の設定だけで HTTPS 化可能。
nginx 等: certbot や acme.sh と組み合わせて Let's Encrypt 自動化 (= cron で更新)

[after]
Caddy や nginx などの web server で取得 + 運用可能。
```

= 「先生視点では「何で実現できるか」 が分かれば十分」、 実装 detail は実装者の領域。

### 1-2. 期間 / 数値情報削除

```
[before]
有効期限 1 年、 毎年手動更新が必要 / 有効期限 90 日ですが自動更新

[after]
(= 削除、 受信者の判断材料でなければ)
```

### 1-3. 括弧の中身を main statement に統合 or 削除

```
[before]
内部 wiki に詳しい手順あります (= 鍵 + CSR 作成 → ITC に提出 → 配置の流れ)。
[after]
内部 wiki に詳しい手順: <URL>
```

### 1-4. if 節の必須感を削る

```
[before]
もし先生サーバが docker などで構築されているのであれば、 Caddy を ...

[after]
具体的な構成は kamoike-oval-serv の運用方法 (= docker / 直接 host / etc.)
を教えていただければ、 構成例をお送りできます。
```

= docker 必須感が消える、 docker でなくても OK というニュアンス。

## 2. 暗示 patterns

### 2-1. 「自分で調べて」 → ネット記事への誘導

```
[before]
詳しくは google で調べてください。

[after]
ネット上に事例も豊富なので参考になるかと思います。
```

### 2-2. 「先生は知らないかも」 → さりげない link 提示

```
[before]
内部 wiki を見ておいてください。 手順あります。

[after]
内部 wiki に詳しい手順あります: <URL>
```

= link 提示で「読んで」 を直接言わない。

## 3. forwarding patterns

### 3-1. 「他に聞いて」 → 担当者振り

```
[before]
僕はよく分からないので他の人に聞いてください。

[after]
jn 内の具体的な構成事例は jnweb 担当の @aokiti さんに聞いていただくのが
早いかもしれません。
```

### 3-2. 「@担当者 さんに振る」 ニュアンス調整

```
[before]
@aokiti に聞いて。

[after]
@aokiti さんに聞いていただくのが早いかもしれません。
```

= 「いただく」「かもしれません」 で柔らかく。

## 4. 余談線 patterns

### 4-1. 「やってほしい」 → 温度感ゼロ提案

```
[before]
github にあげてくれると助かります。 そうしてください。

[after]
(余談ですが、 kamoike-oval-serv の構成を github に上げていただけると、
jn ops 側からも PR で改善提案などできて便利かもしれません。
ご希望あれば、 という温度感で。)
```

= 「温度感で」「ご希望あれば」 で強制感ゼロ。

### 4-2. 余談は括弧で本文と分離

```
本文 ...

(余談ですが、 ... 温度感で。)

よろしくお願いいたします。
```

## 5. 関連事項の自然な併記 pattern

### 5-1. 主依頼 + 関連 work の事前通知

```
お手数ですが、 該当ネットワークから疎通確認をお願いいたします (本依頼 a).

なお HTTPS 化に伴い、 firewall の TCP/3000 開放は不要になり、 代わりに
TCP/80 + TCP/443 の開放が必要になるかと思います (関連 work b).
タイミング教えていただければこちらで対応します。
```

= 主依頼への返信 + 関連で必要になる別 op を **先回り提示**、 親切印象。

## 6. 矛盾 / 重複の自動 cleanup

反復推敲のたびに以下を自動チェック:

| パターン | NG 例 | OK 例 |
|---|---|---|
| 助詞重複 | 「NII のは更新作業がITCとの連携が必要なので」 | 「NII のは更新作業や ITC との連携が必要になります」 |
| 同句反復 | 「が多いので、 が多いので、」 | 「が多く、」 |
| tone 混在 | 「お疲れ〜 ... よろしくお願いいたします」 | tone 統一 (= 全 polite or 全 casual) |
| 過剰 emoji | 「追加しました 🙏✨ お試しください 🎉」 | 「追加しました 🙏」 or 絵文字なし |
| 括弧過多 | 「(= ...) (= ...) (= ...)」 | 1-2 個までに集約 |

## 7. placeholder と user 記入箇所

draft 内に user が後で fill in する箇所がある時、 **明示的に placeholder で残す**:

- URL: `<wiki URL を入れてください>`
- mention: `<@担当者>` (= 担当者の username 不明時)
- 日付: `<送信日>`
- 自分の名前: `<xx>` (= jnroot 担当者名等)

output 末尾で「以下の placeholder を fill in してください」 と列挙する案もあり。

## 8. NG patterns まとめ

- prescriptive 文言 (= 「絶対」「必ず」「すべき」「お願いします」 強要型)
- 受信者の前提条件を仮定 (= 「nc 使ってください」「docker でしょ」)
- detail 過剰 (= 自動更新サイクル、 内部実装、 数値情報の不要羅列)
- 暗示 / 余談線の強制感 (= 「github に上げて」 直接命令型)
- tone 混在 (= 開頭 casual + 閉じ formal)
