# AI 文章の脱臭ルール

## 概要

AI が生成した文章をそのまま出すと「実際に検証していないのでは」と疑われる。
OSS の README ではスパム扱いされることもある。
このスキルは生成テキストから「AI くささ」を除去し、信頼されるトーンに仕上げるためのルールを定める。

対象: 技術ドキュメント、PR 文書、README、コミットメッセージ、report.md 等すべての文書。

academic 文書に特化した脱臭は `../arx-ai-deodorize/SKILL.md` を、
より広範な academic 執筆 polish は `../arx-writing-polish/SKILL.md` を参照。
本 skill は汎用の脱臭 rule として academic 以外のドキュメントも対象にする。

---

## 声とトーン

### 目指す声

「詳しい同僚が、落ち着いて、今すぐ役に立つ手順を教えてくれる」感じ。
Google のドキュメントガイドは「会話的で、親しみやすく、押しつけがましくない声」と定義している ([Google][3])。
Microsoft は「暖かく、はっきりしていて、助けになる声。普通に話すように書け」としている ([Microsoft][1])。

### 実践ルール

- 読者を「あなた / you」として直接扱い、能動態で書く ([Google][5])
- 見出しは動詞から始める。「Configure X」は良い。「Configuring X」は避ける ([Grafana][2])
- 文は短く。読点が 3 つ以上ある文は分割する ([Microsoft][4])
- 日本語の技術文書では常体（〜する / 〜である）で統一する

---

## 禁止事項

以下に該当する表現が残っていたら修正対象とする。

| パターン | 具体例 | 対処 |
|---------|--------|------|
| 抽象スローガンの前置き | 「近年の急速なデジタル化に伴い〜」「本プロジェクトは革新的な〜」 | 削除して本題から始める |
| バズワード | "革新的" "シームレス" "cutting-edge" "エンドツーエンド" "revolutionize" | 具体的な動詞・名詞に置き換える |
| テンプレ締め | "By following these steps, you'll be on your way to success." | 次の具体的アクションで終える |
| 主体をぼかす受動態 | "It is recommended that ..." "〜されることが望ましい" | 「X を使う」「Y を実行する」に書き直す |
| 文体の混在 | 「〜していただけますと幸いです」→次の行で「実行する」 | 常体に統一する |
| 無内容なカタカナ英語 | 「ディスラプティブなエクスペリエンスをデリバーする」 | 素直な日本語か英語そのままにする |
| 長すぎる一文 | 読点 4 つ以上、接続詞で繋ぎ続ける文 | 箇条書きか複数文に分割する |
| 過剰な修飾 | 「非常に重要な」「極めて効果的な」「包括的な」 | 修飾語を削って事実だけ残す |

## 日本語特有ルール

AI が日本語文書を生成すると崩れやすいポイント。

1. **文体は常体で統一** -- 「〜する / 〜である」で通す。「〜してください」「〜いただけます」は使わない
2. **手順は叙述で書く** -- 「1. 依存関係をインストールする」の後にコマンド例と結果を続ける。命令口調にならず角が立たない
3. **結果を明記する** -- コマンドの後に「`http://localhost:3000` が起動する」のように成功状態を書く ([Grafana][2])
4. **表記ゆれを抑える** -- "repository" と "リポジトリ" を同一文書内で混在させない。英語かカタカナかを決めて統一する
5. **カタカナ英語の乱造を避ける** -- 「フィーチャーブランチ」「リクエストプル」より「feature branch」「Pull Request」をそのまま使う
6. **ステータスは正直に書く** -- 未完成なら "WIP" と書く。実態と違うポジショントークは不信に直結する

### プロジェクト固有ルール優先

プロジェクトの CLAUDE.md や `order/.claude/rules/` (`coding/commit.md` 等) にコミットメッセージやドキュメントの文体規定がある場合、そちらが優先する。
このスキルの汎用ルールとプロジェクト固有ルールが矛盾する場合、プロジェクト固有ルールに従う。

例:
- コミットメッセージの言語（日本語 / 英語）や prefix 慣例 (`feat():` 等) はプロジェクト規約が優先
- ドキュメント body の常体 / 敬体切替、`file:line` 根拠明示ルール等はプロジェクト規約が優先

## セルフチェック

文書を確定する前に以下の 3 観点で検査する。1 つでも不合格なら修正して再検査する。

### A. 再現性（読者が手を動かせるか）

| # | チェック項目 | 合否 |
|---|------------|------|
| 1 | この文書だけで読者が最小手順を実行できるか | |
| 2 | コマンドは検証済みか（コピペで動くか） | |
| 3 | 実行後の成功状態が明示されているか | |
| 4 | 前提条件（環境、バージョン等）が書かれているか | |

### B. 声とトーン（人間が書いたように読めるか）

| # | チェック項目 | 合否 |
|---|------------|------|
| 1 | 声に出して読んでロボットに聞こえないか ([Microsoft][1]) | |
| 2 | 営業っぽい前置きや抽象スローガンが残っていないか | |
| 3 | 禁止事項リストに該当する表現が残っていないか | |
| 4 | 文体（常体 / 敬体）が統一されているか | |

### C. 構成と可搬性（文脈を共有しない人にも通じるか）

| # | チェック項目 | 合否 |
|---|------------|------|
| 1 | チーム固有の前提（VPN、社内 URL 等）が紛れ込んでいないか | |
| 2 | 紛れ込んでいる場合、別ファイルに分離したか | |
| 3 | リンクは相対パスか、壊れにくい形式か | |

3 観点すべて合格したものだけを確定版とする。不合格の場合は該当箇所を修正し、再度全項目を通す。

## 注意事項

- このスキルは `user-invocable: false` であり、他のスキルや文書生成フローから暗黙的に参照される
- 「脱臭」は完璧を目指すものではなく、明らかな AI 臭を除去することが目的
- 内容の正確さ（技術的に正しいか）はこのスキルの範囲外。別途レビューで担保する
