# reimagine - ゼロベース再設計レポート

「もしゼロから自由に作り直せるなら」の視点で現行プロジェクトを再評価し、
理想設計と移行プランをレポート出力する。コードは変更しない。

## Step 1: 偵察

対象: `$ARGUMENTS` で指定されたディレクトリ、または現在のプロジェクト。

以下を素早く把握する（ユーザーには結果だけ報告）:

```bash
# 変更頻度の高いファイル = 痛みの所在
git log --since="6 months ago" --pretty=format: --name-only | sort | uniq -c | sort -rn | head -20
```

- ディレクトリ構造 → アーキテクチャの全体像
- 依存管理ファイル (package.json, pyproject.toml 等) → 技術スタック
- README, CLAUDE.md, docs/ → 設計意図
- エントリポイントとコアモジュールのシンボル概要 → レイヤー構造
- 上記 git log → 変更集中箇所 = 設計上の痛み

## Step 2: 再設計の思考

3つの問いに答える:

**捨てるもの**: 歴史的経緯でこうなっただけの部分、過剰な抽象化、技術選定のミスマッチ

**残すもの**: 正解だった設計判断、ドメインロジックの核（フレームワークは変えられるがビジネスロジックは資産）

**理想の姿**: 制約を外して考えた最適解。アーキテクチャ、スタック、データモデル、API、テスト、運用

## Step 3: 移行プラン

理想を現実に落とし込む。4段階:

| 区分 | 期間 | 基準 |
|------|------|------|
| Quick Wins | 今週 | リスク低・効果高 |
| Medium-term | 1-3ヶ月 | 設計変更を伴う改善 |
| Long-term | 3ヶ月+ | アーキテクチャ変更 |
| やらない | - | コスト対効果が合わない |

## Step 4: レポート出力

`reimagine-report-YYYYMMDD.md` として出力。order ベースのワークフローでは当該フェーズの `appendix/` に配置する。

> **注意**: Step 1-4 はスキル内部の分析工程であり、order の phases に 1:1 で展開しないこと。
> reimagine 全体が order 上の 1 フェーズ（例: phase_001）に収まるのが正しい構造。


## うまくいかないとき

- プロジェクトが小さすぎる（ファイル数 < 10） → 再設計より作り直した方が早い旨を伝える
- git 履歴がない → 変更集中箇所の分析をスキップし、コード構造のみで判断
- モノレポで対象が不明確 → ユーザーに対象サブディレクトリを確認する
