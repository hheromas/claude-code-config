# タスクワークフロー

大規模タスク実行、自己批評、ファイル再編成のパターン。

## Phase と Step の判定

- **Phase**: 独立成果責任単位。固有の成果物と完了/失敗条件を持つ
- **Step**: Phase 内の実行手順。`work/` に記録

| Phase にする | Step にする |
|-------------|------------|
| 単体でレビュー可能な成果物がある | 前後と一体でないと成果物にならない |
| 単独の完了/失敗条件を定義できる | 「前工程の続き」でしかない |
| 並列化や独立再実行にメリットがある | 強い直列依存 |
| タスク固有の意思決定を含む | 毎回必須の定型手順 |

SC-3R・Git commit・plan.md 更新は定型手順のため原則 Step。

**アンチパターン**: SC-3R 各ラウンドや commit の独立 Phase 化、「shellcheck」等の手段だけで Phase を作る、強依存の連続作業の Phase 過分割。

## RPI バリデーションゲート (Research → Plan → Implement)

各フェーズ移行時にゲートチェックを実施:

- **Research → Plan**: 調査エビデンス（ファイルパス、grep 結果、依存関係マップ）が work/ に記録されていること。推測ベースの計画立案は禁止
- **Plan → Implement**: plan.md が存在し、Phase/Step が定義済みであること。計画なしの実装着手は禁止
- **Implement → Commit**: plan.md の成功基準と照合し、品質チェックコマンドがすべてパスしていること

ゲート未通過の場合は前フェーズに戻り、不足を補完する。

## 実装前の影響調査

実装 Phase 開始前に Step として実施:

- 修正対象ファイル・コンポーネントの全リスト作成
- grep/find_referencing_symbols で全参照箇所を列挙
- 破壊的変更リスク（型変更、インターフェース変更、削除）の評価
- 変更しない箇所とスキップ理由の明記

## Phase 追加の判断基準

- **トリガー**: レビュー指摘、コードレビュー REJECT、検証環境での不具合
- plan.md に追加理由を1行で記録、番号は連番

## 自己批評（全タスク必須）

タスク完了時（複数フェーズの場合は各フェーズ完了後）に自己批評チェックポイントを設ける：

1. 期待値と実際の結果を表形式で比較
2. 差異があれば理由を明記
3. PASS/FAIL を判定してから次フェーズへ進む

レポート内で `file:line` 形式の引用を行う場合、実際のファイル行数を確認し、存在しない行番号を記載しないこと。

### SC-3R (Self-Critique 3 Rounds)

| Round | 対象 | 検証項目 |
|-------|------|---------|
| **1** | 構造検証 | CLAUDE.md 標準準拠、フォルダ命名、必須ファイル存在 |
| **2** | 整合性検証 | order↔report 対応、参照パス整合性、plan.md との一致 |
| **3** | 最終検証 | 成果物品質、ユーザー要件、見落としチェック |

FAIL が出た場合は修正後に再検証してから次へ進む。

→ 詳細テンプレート・エビデンス評価は /self-critique を参照

### 過去の知見に対する誠実さ

- 実際に読んでいないファイルの内容を推測で語らない
- 過去の Phase を正確に把握できていない場合は、素直に「未確認」と申告し精読ステップを提案する
- 新しい分析を提案する前に、同等の分析が過去に実施済みでないか work/ の記録を検索する

### 残タスク棚卸し時の DUMP 参照義務

残タスクの棚卸しや次セッションの引き継ぎを行う際は、work/ の過去ダンプファイルを必ず参照すること。記憶や推測ではなく、ファイルに記録された事実に基づいて判断する。

### Meta-TODO パターン（自走セッション用）

自走セッションでは「TODO を追加する TODO」を含め、問題解決まで自律的に継続する。各ステップで次にやるべきことを TODO として追加し、空になるまで回す。

## work/ への随時ダンプ義務

- **原則**: think → dump → act（考えたら書く、書いてから動く）。「後でまとめる」「report.md に直接書く」は禁止
- **命名**: `P{XX}_STEP{N}_{内容}.md` 厳守。作成前に `ls work/` で既存番号を確認し衝突を回避
- **commit**: ダンプしたら order repo も commit する

### 大量ファイル精読時の逐次 dump

- 1 Phase（または論理的な単位）を読むごとに知見をファイルに書き出す。一括読み込み後のまとめ禁止
- subagent 委託時は 1 バッチ 30 ファイル以下に分割。各知見に必ずソースファイルパスを記載
- 2-3 単位ごとにセーフティコミットを入れる

### SoT Hierarchy（長期 Phase 向け）

10+ STEP の見込み、または 3+ セッションにまたがる Phase では 3 層構造を採用する。新規 Phase に適用。既存 Phase への遡及は不要。

- **STEP001 (Session Info)**: 不可変。セッション構造・参照パス・Phase スコープ
- **STEP002 (SSOT)**: 常時更新。現在地（1-2行）+ Section SoT レジストリ（Section 名 + STEP 範囲）。簡潔に保ち、個別 STEP の一覧は各 Section SoT に委任
- **Section SoT**: 作業領域（※）ごとの詳細追跡ファイル。work/ に配置。Section 開始時に宣言し STEP002 に登録。担当 STEP 範囲内の個別 STEP 一覧を管理

（※）Section = Phase 内の論理的な作業単位（例: スクリプト設計、実験実行、データ分析、論文執筆）。独立した追跡が必要な粒度で区切る。

ルール:
- 新 STEP 作成時に、所属 Section SoT の STEP 一覧に追記する。新 Section の場合は STEP002 のレジストリにも登録
- Supersede chain: 新 STEP ヘッダに `Supersedes: STEPXXX`。一覧では `→` 表記
- STEP 数が増えた Section は範囲分割してよい（例: STEP004-050 → Section A、STEP051-100 → Section B）

見落とし検出:
- SC-3R R1 で `ls work/` と Section SoT の STEP 一覧を突合し、未登録を検出する（ベストエフォート。サブ番号 10a/10b 等がある場合は完全一致を求めない）

## ファイル再編成ワークフロー

既存のファイル構造を標準に準拠させる際のワークフロー。

```
Phase 1: 調査・設計（成果物: 差分分析 + 設計書 + ファイルマッピング）
Phase 2: 再配置 + ドキュメント整備（成果物: 再編成後ツリー + report.md）
  Steps: ファイル操作 → ドキュメント整備 → plan.md 更新 → SC-3R → commit
```

→ 差分分類・設計書要件・実行ルールの詳細は /reorganize を参照

## コード動作の説明時は「推測ゼロ」で事実固定する

- 必ず `ファイル名:行番号` で根拠を示す。「〜と思われる」「〜の可能性がある」は禁止
- 特定できない場合は「未確定（根拠未発見）」と明記
- 比較表で差異を明示し、各セルに根拠（ファイル:行番号）を記載

## subagent 並列実行の依存関係制約

- 後段の STEP が前段の結果を参照する場合、並列実行してはならない
- 並列実行が許可されるのは、完全に独立した分析タスク（例: SC-3R の各ラウンド）のみ

## 事実修正のクロスファイル検証

修正前に grep で関連ファイルを一括チェックし、同じ誤記を全ファイルで同時修正すること。

## セーフティコミット

Phase 境界（開始時・終了時）でコミットを行い、成果物の喪失を防ぐ。

## 所要時間の見積もりは実測ベースで計算する

推測や概算で見積もりを出さず、実測データに基づいて計算する：

1. 過去の類似タスクから単位あたりの所要時間を算出
2. parallel / sequential を明確に分離して構造を明示
3. 前提条件の差異があれば明記
4. 計算式を必ず提示（例: `(1.5h/unit × 12 units) / 4 parallel = 4.5h`）

## バックグラウンドエージェント同時起動の上限

同時 **10 本以下** に制限する（推奨 cap-10、 context limit 到達時は要 monitoring + 縮小）。依存関係制約も同時に遵守すること。

- Rationale: 2026-05-08 user mandate で cap-3 → cap-10 raise（skill-redesign Phase 2.8 BG-V3）。 large-scale dispatch (16+ implicit rule audit, multi-batch BG verify 等) の throughput 改善目的
- 縮小条件: context limit alert / token budget 80%+ / dependency violation 検出時は cap を 3-5 に縮小
- 依存関係制約は前項「subagent 並列実行の依存関係制約」を厳守

## Context compaction 後の復帰

SoT Hierarchy 採用時: STEP001 → STEP002 → 現在の Section SoT の順に読む。
未採用時: `ls work/` → 最新 STEP を Read → plan.md の Phase ステータス確認。
記憶に頼らない。

## 安易な完了宣言の禁止

「上限到達」「これ以上できない」を根拠なく宣言しない。plan.md の成功基準と照合して充足状況を明示すること。

## plan.md と現状の乖離時

plan.md は SSOT だが、現状と明らかに乖離している場合は盲従せずユーザーに報告し更新を提案する。Phase のスキップや順序変更は引き続き禁止。
